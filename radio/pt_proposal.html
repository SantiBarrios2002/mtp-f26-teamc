Protocol and firmware proposal

From Radio Team (Santiago, Andrian, Marcos)To Ibrahim, Guillem, SofiaVersion 0.2 · Wed 7 Oct 2026

The radio team has fixed the physical layer: 868 MHz, RFM69, 100 kbps, with a tested driver. Everything above it belongs to protocols & software. This is a starting proposal built from the competition rules and our link numbers, to speed you up. It is not a decision. Please change whatever you see better.

In short

  1. Compress the file as one deflate stream. On English text in 100-byte lines it measured ~3×. The whole file then crosses in ~40 s instead of ~119 s, and each round uses a third of the transmit time, so ≈9 rounds per hour fit the 10 % duty limit instead of 3.
  2. Selective-repeat ARQ with bursts of 16 frames and one bitmap ACK. Frames are delivered strictly in order, because only the first unbroken run of correct lines counts.
  3. Resume after any interruption. A HELLO handshake identifies the file, and the receiver keeps its progress, so an "attack" or a reboot costs seconds, not the round.
  4. Network Mode: gossip, not routing. Every node rebroadcasts the small file (~9 frames) on a randomised timer (Trickle-style). No addresses or positions are needed, every node ends up with a copy (that is how teams win NM), and it uses about 1–2 % of the duty budget. It needs agreement with all teams.
  5. Firmware: C on the Pico SDK, with the radio loop on one core and USB/flash/compression on the other. Build a PC simulator first so the protocol is tested before boards exist.

Frame formats

Each radio frame carries at most 64 bytes after the length byte. A full DATA frame takes 5.84 ms on air at 100 kbps.

type|flags1 B
session1 B
seq2 B
compressed file bytes≤ 60 B
CRC2 B · radio

DATA, SRI/MRM. Length byte 64 at most; the radio adds and checks the CRC (profile SRI_100K). session is a random byte chosen at HELLO, so frames from earlier runs or other teams are dropped.

type|flags1 B
session1 B
next_seq2 B
bitmap2 B
rssi1 B
CRC2 B · radio

ACK. next_seq = every frame before it has arrived. bitmap bit i = frame next_seq+1+i arrived. The receiver also reports the RSSI it measured, for link logging.

type1 B
session1 B
file_len4 B
file_crc324 B
codec1 B
name≤ 24 B
CRC2 B · radio

HELLO (sender) and HELLO_ACK (receiver; replaces name with next_seq). They identify the file, so a rebooted receiver can resume where it stopped.

Type values (proposal): 0x01 DATA, 0x02 ACK, 0x03 HELLO, 0x04 HELLO_ACK, 0x05 END, 0x4E NM_DATA. Flags: last-in-burst, retransmission.

Link procedure (SRI and MRM)

sequenceDiagram
  participant TX as Sender (role switch = TX)
  participant RX as Receiver (role switch = RX)
  Note over TX,RX: GO: both buttons pressed
  loop until HELLO_ACK
    TX->>RX: HELLO(session, file_len, crc32, codec, name)
    RX-->>TX: HELLO_ACK(next_seq)  [0 on a fresh start, >0 on resume]
  end
  loop until the whole file is acknowledged or STOP
    TX->>RX: DATA × 16 (missing first, then new)
    RX-->>TX: ACK(next_seq, bitmap, rssi)
  end
  TX->>RX: END
  Note over RX: STOP: decompress what arrived in order, save to flash, then to USB

Timing

  • Burst of 16 × 64 B frames: 93 ms
  • ACK + 2 radio turnarounds: ≈ 4 ms
  • ACK timeout: ≈ 24 ms at 100 kbps (scales with bit rate), then resend the burst
  • Goodput (model, with 15 % software overhead): ≈ 67 kbps

Resend rules

Each burst first resends every frame the last bitmap marked missing, then fills with new frames. The window never advances past a gap, so the receiver's output is always one continuous run.

After 20 silent timeouts, drop to the 38.4 kbps profile and send HELLO again. Never give up before STOP.

Recovering from attacks

Jamming or shadowing only looks like lost ACKs, and the retry loop covers it. A reboot of either box is handled by HELLO. The receiver keeps next_seq and the data in flash, and the sender re-reads the file from flash.

Hardware watchdog on both cores, plus brown-out reset.

Network Mode: gossip proposal for all teams

No node knows its position, and the rules forbid a position switch. The file is only about 500 B, or 9 frames. So we suggest that nothing is routed: every node that holds part of the file rebroadcasts it on a randomised timer, following the Trickle algorithm (IETF RFC 6206), until STOP.

type 0x4E1 B
file_id2 B
idx1 B
total1 B
file bytes≤ 57 B
CRC-16 sw2 B

NM_DATA: the inter-team standard on the NM_COMMON radio profile. file_id = CRC-16 of the whole file. The CRC is computed in software (CCITT-FALSE, big-endian) because different radio chips use different hardware CRCs.

Behaviour

  • The sender (SW corner) starts with the whole file.
  • Every node keeps every valid chunk with the same file_id. When it hears its first new chunk, it starts rebroadcasting everything it holds.
  • Rebroadcast interval: random in [I/2, I], starting at I = 1 s and doubling up to 8 s. Skip a turn if 3 or more identical copies were heard in that interval.
  • Once all total chunks check out, the node writes the file to flash and saves it to USB after STOP.

Why it fits

  • No addresses or positions, so it works in any random order of teams.
  • Every node ends up with a copy, which is the win condition. That makes the +2 bonus, and the +0.5 "poker bonus" for all teams, likely.
  • Duty cost: about 51 ms per full rebroadcast, roughly 60–100 rebroadcasts in 5 min, so 3–5 s of TX (about 1 % of the hourly budget).
  • Simple enough for every team to implement on CC1101, RFM69 or Si4463.

To agree with the other teams

  • The frame above, the radio settings (radio team's NM draft) and the timer values.
  • An interop day before week 6: every team's box in one room, at the bench frequency (869.85 MHz).
  • Protocols & software leads this with the other teams' protocol people; the radio team handles the radio settings.

MRM: open, decide in weeks 8–9 with the radio team

All teams transmit at the same time, 260 m apart. If every team stays in 869.40–869.65 MHz, they share 250 kHz. Options:

  • Listen before talk using the RFM69 RSSI before each burst, with random backoff. Works with no agreement, but the throughput is shared.
  • Agreed time or frequency split between teams (e.g. 5 × 50 kHz at 19.2 kbps): predictable, about 2 000–4 000 lines each before compression.
  • 2.4 GHz add-on for MRM only (a radio-team decision, D-R4).

Software ask for now: keep the radio profile and the channel-access policy switchable at run time, so the choice doesn't need a rewrite.

Pico pitfall: erasing or writing flash stalls code that runs from flash on both cores. Keep the radio loop in RAM (__not_in_flash_func), buffer received data in RAM, and write flash in 4 KB sectors between bursts. Test this early, because it is the classic way to lose a round.

Simulator: built, first results new 7 Oct

The radio team built the simulator in proto/. It runs the same C protocol code planned for the Pico (link with resume, NM gossip, deflate) against a modelled channel:

  • half-duplex radios, with airtime from the real driver;
  • collisions, and random or bursty loss;
  • a jamming blackout, and reboots;
  • the real duty-cycle guard.

Scoring copies the judges: decompress, then count the first unbroken run of identical lines. make -C proto test runs 11 scenarios in about 1 second.

It already caught a bug. With fixed timeouts, the 38.4 kbps fallback delivered only 883 lines. One frame (15.2 ms) outlasted the receiver's 15 ms idle-ACK timer, so the receiver ACKed in the middle of bursts and went deaf. All timeouts are now derived from the bit rate.

Still open in the simulator: an MRM scenario with several teams, listen-before-talk, automatic profile fallback, and loss taken from measured packet-error rates instead of fixed percentages. Assumptions to measure on the bench: 1 ms turnaround, 0.5 ms gap between frames.
