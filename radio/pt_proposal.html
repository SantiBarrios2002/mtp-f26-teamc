Protocol and firmware proposal

From Radio Team (Santiago, Andrian, Marcos)To Ibrahim, Guillem, SofiaVersion 0.3 · Fri 9 Oct 2026

New in v0.3: all four teams moved to 2.4 GHz. The radio is now the nRF24L01+ (Ebyte E01-ML01DP5) at 250 kbps, so frames are at most 32 B, each team has its own channel in MRM, and there is no duty-cycle limit any more. The protocol code and the simulator were ported; all 11 scenarios pass.

The radio team has fixed the physical layer: 2.4 GHz, nRF24L01+, 250 kbps, with a tested driver. Everything above it belongs to protocols & software. This is a starting proposal built from the competition rules and our link numbers, to speed you up. It is not a decision. Please change whatever you see better.

In short

  1. Compress the file as one deflate stream. On English text in 100-byte lines it measured ~3×. The whole file then crosses in ~17 s instead of ~50 s (model, no loss), which leaves most of the 2 minutes to recover from attacks. The simulator, at 5 % loss, needs 28 s with compression and 73 s without.
  2. Selective-repeat ARQ with bursts of 16 frames and one bitmap ACK. Frames are delivered strictly in order, because only the first unbroken run of correct lines counts.
  3. Resume after any interruption. A HELLO handshake identifies the file, and the receiver keeps its progress, so an "attack" or a reboot costs seconds, not the round.
  4. Network Mode: gossip, not routing. Every node rebroadcasts the small file (~20 frames) on a randomised timer (Trickle-style). No addresses or positions are needed, and every node ends up with a copy (that is how teams win NM). It needs agreement with all teams.
  5. Firmware: C on the Pico SDK, with the radio loop on one core and USB/flash/compression on the other. Build a PC simulator first so the protocol is tested before boards exist.

Frame formats

Each radio frame carries at most 32 bytes (nRF24 dynamic payload). A full DATA frame takes 1.32 ms on air at 250 kbps.

type|flags1 B
session1 B
seq2 B
compressed file bytes≤ 28 B
CRC2 B · radio

DATA, SRI/MRM. 32 B at most; the radio adds and checks the CRC (profile TEAM_250K). The 16-bit seq covers files up to 1.83 MB. session is a random byte chosen at HELLO, so frames from earlier runs or other teams are dropped.

type|flags1 B
session1 B
next_seq2 B
bitmap2 B
link1 B
CRC2 B · radio

ACK. next_seq = every frame before it has arrived. bitmap bit i = frame next_seq+1+i arrived. The last byte is for link logging: the nRF24 has no RSSI, so it carries the RPD bit (signal above about −76 dBm at the antenna).

type1 B
session1 B
file_len4 B
file_crc324 B
codec1 B
name≤ 21 B
CRC2 B · radio

HELLO (sender) and HELLO_ACK (receiver; replaces name with next_seq). They identify the file, so a rebooted receiver can resume where it stopped.

Type values (proposal): 0x01 DATA, 0x02 ACK, 0x03 HELLO, 0x04 HELLO_ACK, 0x05 END, 0x4E NM_DATA. Flags: last-in-burst, retransmission.

Link procedure (SRI and MRM)

sequenceDiagram
  participant TX as Sender (role switch = TX)
  participant RX as Receiver (role switch = RX)
  Note over TX,RX: GO: both buttons pressed
  loop until HELLO_ACK
    TX->>RX: HELLO(session, file_len, crc32, codec, name)
    RX-->>TX: HELLO_ACK(next_seq)  [0 on a fresh start, >0 on resume]
  end
  loop until the whole file is acknowledged or STOP
    TX->>RX: DATA × 16 (missing first, then new)
    RX-->>TX: ACK(next_seq, bitmap, rssi)
  end
  TX->>RX: END
  Note over RX: STOP: decompress what arrived in order, save to flash, then to USB

Timing

  • Burst of 16 × 32 B frames: ≈ 26 ms (1.32 ms each + 0.3 ms gap)
  • ACK + 2 radio turnarounds: ≈ 2.5 ms
  • ACK timeout: ≈ 11.6 ms at 250 kbps (scales with bit rate), then resend the burst
  • Goodput (model, with 15 % software overhead): ≈ 159 kbps

Resend rules

Each burst first resends every frame the last bitmap marked missing, then fills with new frames. The window never advances past a gap, so the receiver's output is always one continuous run.

After 8 silent timeouts, send HELLO again with backoff. 250 kbps is already the nRF24's slowest rate, so there is no slower fallback. Never give up before STOP.

Recovering from attacks

Jamming or shadowing only looks like lost ACKs, and the retry loop covers it. A reboot of either box is handled by HELLO. The receiver keeps next_seq and the data in flash, and the sender re-reads the file from flash.

Hardware watchdog on both cores, plus brown-out reset.

Network Mode: gossip proposal for all teams

No node knows its position, and the rules forbid a position switch. The file is only about 500 B, or 20 frames. So we suggest that nothing is routed: every node that holds part of the file rebroadcasts it on a randomised timer, following the Trickle algorithm (IETF RFC 6206), until STOP.

type 0x4E1 B
file_id2 B
idx1 B
total1 B
file bytes≤ 25 B
CRC-16 sw2 B

NM_DATA: the inter-team standard on the NM_COMMON radio profile. file_id = CRC-16 of the whole file. The radio's CRC protects each hop; the software CRC (CCITT-FALSE, big-endian) checks the data end to end across relays.

Behaviour

  • The sender (SW corner) starts with the whole file.
  • Every node keeps every valid chunk with the same file_id. When it hears its first new chunk, it starts rebroadcasting everything it holds.
  • Rebroadcast interval: random in [I/2, I], starting at I = 1 s and doubling up to 8 s. Skip a turn if 3 or more identical copies were heard in that interval.
  • Once all total chunks check out, the node writes the file to flash and saves it to USB after STOP.

Why it fits

  • No addresses or positions, so it works in any random order of teams.
  • Every node ends up with a copy, which is the win condition. That makes the +2 bonus, and the +0.5 "poker bonus" for all teams, likely.
  • TX time: about 33 ms per full rebroadcast; in the simulator the busiest node transmits about 1.1 s in 5 min. No duty-cycle limit at 2.4 GHz.
  • Simple enough for every team to implement on any nRF24L01+ board.

MRM: one channel per team

All teams transmit at the same time, 260 m apart. At 2.4 GHz each team gets its own channel, so each keeps its full rate. The radio team's draft for the four teams is RF_CH 24 / 49 / 74 / 82 (D-R4), to be agreed after the campus WiFi survey.

  • The risk is a neighbouring team's box a few metres away, which can arrive 40–55 dB above our partner. Channel spacing and distance between boxes handle it (radio brief, MRM section).
  • Listen before talk with the RPD bit before each burst stays an option if a channel turns out to be shared with WiFi.

Software ask for now: keep the channel number and the channel-access policy configurable at run time, so the final plan doesn't need a rewrite.

Pico pitfall: erasing or writing flash stalls code that runs from flash on both cores. Keep the radio loop in RAM (__not_in_flash_func), buffer received data in RAM, and write flash in 4 KB sectors between bursts. Test this early, because it is the classic way to lose a round.

Simulator: results on the nRF24 radio updated 9 Oct

The radio team built the simulator in proto/. It runs the same C protocol code planned for the Pico (link with resume, NM gossip, deflate) against a modelled channel:

  • half-duplex radios, with airtime from the real driver;
  • collisions, and random or bursty loss;
  • a jamming blackout, and reboots.

Scoring copies the judges: decompress, then count the first unbroken run of identical lines. make -C proto test runs 11 scenarios in about 1 second.

It already caught a bug (on the old 868 MHz radio). With fixed timeouts, the 38.4 kbps fallback delivered only 883 lines. One frame (15.2 ms) outlasted the receiver's 15 ms idle-ACK timer, so the receiver ACKed in the middle of bursts and went deaf. All timeouts are now derived from the bit rate.

Still open in the simulator: an MRM scenario with four teams on their own channels, listen-before-talk, two radios per box, and loss taken from measured packet-error rates instead of fixed percentages. Assumptions to measure on the bench: 1 ms turnaround, 0.3 ms gap between frames.
